## Bugs found and fixed (all verified with evidence)

1. **GDAL/GEOS never loaded on Windows — hard startup blocker.** `config/settings.py` assigned
   `GDAL_LIBRARY_PATH`/`GEOS_LIBRARY_PATH` as *local* variables inside `if os.name == "nt"`, so they
   never reached the module namespace Django reads. Also Django only probes names like `gdal310`, while
   rasterio vendors `gdal-<hash>.dll`. Fixed by extracting `_configure_windows_geospatial_libraries()`
   which declares `global GDAL_LIBRARY_PATH, GEOS_LIBRARY_PATH` and globs `gdal*.dll` / `geos_c*.dll`.
2. **`collectstatic` aborted with `MissingFileError` — production deploy blocker.**
   `assets/css/app.css` pulls in the upstream Tabler webfont stylesheet, which declares `.ttf`, `.woff2`
   AND `.woff` sources, but `scripts/copy-static-assets.mjs` only copied `.woff2`. Manifest static
   storage requires every referenced file to exist. Fixed by also copying `.woff` and `.ttf`.
3. **OR-Tools solver degraded on mid/large instances.** `solve_vrp()` called
   `routing.VehicleVar(index).SetValues(allowed)` for every node even when all vehicles were eligible.
   Measured: 6/8 seeds solved with it, 8/8 without. Fixed to only `RemoveValues()` the ineligible
   vehicles, leaving the domain untouched in the common all-eligible case. Also added a second pass:
   `GREEDY_DESCENT` first (fast, guarantees an answer) then `GUIDED_LOCAL_SEARCH` only if a solution was
   already found and compared by objective value — previously a `TIME_LIMIT` discarded all work.
4. Unit-test "failure" in `tests/unit/test_solver.py` was **environment contention**, not a logic bug —
   it passed once the parallel pip install finished. Synthetic 60-node benchmark that appeared to
   "fail" was actually **over-capacity** (309,836 g demand vs 125,000 g fleet capacity); with an
   adequate fleet the solver assigns all 59 orders across 13 routes with 0 unassigned.
5. **`Exception: CP Solver fail` — core optimization feature crashed on real data.** `solve_vrp()`
   passed `max_duration_s` as the per-vehicle upper bound of the `Time` dimension's CumulVars, but
   CumulVars are absolute seconds from the service-day start. Any stop time window extending past
   `max_duration_s` (here 36,000 s = 10 h, vs seeded windows reaching 55,800 s = 15:30) intersected to
   an empty domain, so OR-Tools aborted **during model construction** at
   `apps/optimization/solver.py` `time_dimension.CumulVar(...).SetRange(*node.time_window)`.
   *Proof:* isolating a single variable showed the horizon, not the window, was decisive —
   `maxdur=86400` → OK, `maxdur=36000` → CRASH, with identical windows and shift.
   **Fix:** horizon now spans the full service day (`_TIME_HORIZON_CEILING = 2*86400`, widened to cover
   every shift/window end), and `max_duration_s` is enforced as a genuine constraint on *elapsed* route
   time (`CumulVar(end) - CumulVar(start) <= max_duration`). Node windows are clamped to the horizon
   instead of crashing. Verified: `max_duration_s` now binds monotonically (7→4→3→1 stops served as the
   budget tightens 36000→12000→9000→6000).
6. **Objective unit inconsistency made the solver drop servable orders.** `_vehicle_input()` scaled the
   currency fixed cost by 100 (`int(vehicle.fixed_cost * 100)` → 15,000,000), while arc cost is
   *metres + seconds* (10³–10⁵) and the unassigned penalty was `1_000_000 × priority_factor`. Opening a
   vehicle therefore always looked more expensive than dropping the order, so orders #3 and #8
   (COLD_CHAIN, trivially servable: 1,436 s elapsed vs 36,000 allowed) were reported unassignable and
   only 1 of 2 vehicles was used.
   **Fix:** introduced an explicit exchange rate `idr_per_objective_unit` (default 100, overridable via
   the profile's `objective_weights_json`) and normalised the fixed cost into objective units. Verified:
   fixed cost 15,000,000 → 1,500; both orders now served; full instance assigns **all 10 orders across
   2 vehicles with 0 unassigned**.

## Notes / gotchas for future sessions

- Times are stored in **UTC** (`USE_TZ=True`, `TIME_ZONE="UTC"`). When checking seeded data, convert
  with `astimezone(ZoneInfo("Asia/Jakarta"))` — naive UTC printing makes 07:00 look like 00:00 and
  invites a false "bug" diagnosis. This cost real debugging time once already.
- `_service_day_start()` returns midnight **in the depot's timezone** (Asia/Jakarta), so solver
  seconds are offset from UTC by the depot's UTC offset.
- Demo drivers have 07:00–17:00 shifts; `max_route_duration_seconds = 36000` (10 h). Only 2 drivers
  exist for 3 vehicles, so a run can use at most 2 vehicles.
- Throwaway probe scripts were used for diagnosis and deleted; keep such experiments out of `scripts/`.

## Seeder hardening — realistic, idempotent demo history (Phase 7 / Task #4)

`apps/common/management/commands/_demo_history.py` drives the **real service layer**
(`optimize_run`, `dispatch_plan`, `record_driver_action`, `record_location`) to build a two-day
operational story, so the demo pages never render empty states. Further bugs found while making it
repeatable:

7. **Timeline read as corrupt data: actuals predated the dispatch.** `dispatch_plan` stamps
   `timezone.now()`, but the field events are backdated onto the service date, so a plan showed
   `dispatched 09:30` with routes starting `08:00`. **Fix:** `_backdate_dispatch()` moves the whole
   run onto the previous evening in a plausible order (solve 17:30 → dispatch 18:00) and rewrites the
   matching `route_plan.dispatched` audit entry. Both routes now derive `start_hour` from
   `route.start_at_planned` instead of a fixed hour, so recorded actuals follow the plan.
8. **`_reset_day` left orphaned rows behind on every re-seed.** Deleting only `RoutePlan` stranded its
   `PlanningRun` (visible in planning history with no plans), left `route_plan.*` `AuditLog` entries
   pointing at deleted plans, and — because `VehicleLocation.route` is `SET_NULL` — orphaned the GPS
   breadcrumbs instead of cascading them away, so the live map accumulated phantom trails
   (22 → 88 rows over two runs). **Fix:** `_reset_day` now also deletes the day's planning runs, the
   audit entries for the deleted plan ids, and route-less `VehicleLocation` rows for the organization.
9. **Exception cleanup filtered on the wrong type.** `_reset_day` deleted
   `type="FAILED_DELIVERY"` but the seeded failure uses `reason_code="CUSTOMER_UNAVAILABLE"`, so
   resolved exceptions piled up (1 → 4) across runs. **Fix:** scope by service date and organization
   rather than by exception type.
10. **`OperationException.created_at` is `auto_now_add`, so backdated failures carried today's date.**
    That would put a day-old service failure in today's triage window. **Fix:** backdate `created_at`
    onto the route cursor right after the failed stop is recorded.
11. **The exception queue had nothing open.** With one failure seeded, `_resolve_demo_exception`
    resolved the *only* exception, leaving zero OPEN items — the triage view looked permanently clean.
    **Fix:** yesterday's plan now also fails one stop, and the resolver only closes exceptions raised
    *before* today. Result: one RESOLVED (yesterday, assigned, resolved +3 h) and one OPEN (today,
    unassigned) — both halves of the workflow visible.

**Verified:** two consecutive `seed_demo` runs produce byte-identical counts (RoutePlan 2, PlanningRun

## Production-readiness audit (portfolio hardening)

A second pass re-audited the repo against a "production-ready portfolio" brief. The project was
already strong (design system, 14 populated surfaces, real PostGIS data), so the work focused on
finding genuine defects instead of restyling. Three real bugs were found and fixed:

12. **Every JWT-protected API endpoint rejected its own caller with 403 — highest severity.**
    `CurrentOrganizationMiddleware` resolves `request.organization` in `process_request`, but DRF
    authenticates *inside the view*. For a bearer request `request.user` is therefore still anonymous
    at middleware time, so the organization stayed `None` and `IsDriver` / `HasOrganization` could
    never match. A driver could present a perfectly valid token and still get 403 from
    `/api/v1/driver/routes/today/`, `/api/v1/live/routes/` and `/api/v1/live/vehicles/`.
    *Proof:* token issue returned 200 while every subsequent driver call returned 403; driver data
    itself was correct (profile present, org 1 ACTIVE, membership role DRIVER).
    **Fix:** extracted `resolve_active_organization(request)` and call it from
    `DocumentedAPIView.initial()` — after DRF authentication, before permission checks. Bearer requests
    are skipped in middleware to avoid resolving against an anonymous user. Verified: all driver
    endpoints now 200 with real payloads (`routes/today` → 1 route with stops/vehicle/geometry);
    session auth unchanged (dashboard 200, KPIs 200, orders API 200); anonymous still 401/403.
    Regression test: `tests/integration/test_driver_token_auth.py`.

13. **`proj.db` missing → any coordinate reprojection raised `GDALException: OGR failure`.**
    `config/settings.py` configured GDAL and GEOS from the rasterio wheel but never pointed PROJ at
    its data directory, so GDAL logged `PROJ: proj_create_from_database: Cannot find proj.db` on every
    spatial operation. The trap: PostGIS does normal spatial math server-side, so `distance_lte`,
    `contains` and geometry round-trips all kept working and the breakage was invisible. Only
    `Point.transform()` in Python failed, and **no current code path calls it** — a latent landmine.
    **Fix:** `_configure_windows_geospatial_libraries()` now sets `PROJ_LIB` to
    `<site-packages>/rasterio/proj_data` when `proj.db` is present, guarded so an empty `PROJ_LIB`
    from `.env.example` still triggers auto-detection. Verified reprojection returns valid Web
    Mercator `(11893997.79, -692517.13)`. Documented in `.env.example` with the "queries still work,
    only reprojection fails" warning.

14. **Flaky solver test (`test_solver_returns_route_and_cumulative_load`) — budget starvation, and it
    was made worse by an earlier fix.** The two-pass search split the budget in half
    (`first_pass_budget = budget_s // 2`). The *first* OR-Tools solve in a process pays for loading and
    initialising the native solver, so with `time_limit_s=1` the first pass received 500 ms, expired
    during cold start, returned `TIME_LIMIT` and discarded a trivially solvable one-stop problem —
    reporting the single order as unassigned. It only reproduced on a cold interpreter (full-suite
    runs took 17–40 s vs 1.3 s warm), which is exactly how it stayed hidden.
    *Proof:* isolated runs passed 6/6; the same test failed inside `pytest tests/unit` after a cold
    start; a warm in-process loop solved the same instance in 0.01–0.18 s.
    **Fix:** the first pass now gets a guaranteed floor, `first_pass_budget = max(5, budget_s // 2)`,
    and the improvement pass only spends `budget_s - first_pass_budget` when that is ≥ 1 s, so it can
    never starve the pass that guarantees an answer. Verified: 12 consecutive cold-process runs green,
    full unit suite 32/32 four times in a row, and quality preserved at scale —
    200 orders → 199/199 assigned, 0 unassigned, 30 s budget finishing in 19.5 s;
    1000-order `RUN_PERFORMANCE_TESTS=1` scale test passes (34.6 s).
    Regression test: `test_found_solution_is_never_discarded_when_the_search_hits_its_budget`.

15. **`ALLOWED_HOSTS` omitted `testserver`, so the whole e2e/API-test path 400'd.**
    Django's test client and Playwright send `Host: testserver`. `.env` listed only
    `127.0.0.1,localhost,0.0.0.0`, so every request was rejected with 400 *before* authentication —
    indistinguishable from a broken login page and the reason the first e2e sweep reported 9 failures.
    **Fix:** append `testserver` to `ALLOWED_HOSTS` only while `DEBUG` is true, keeping deployed host
    lists strict. Verified: login 200, anonymous dashboard 302 → `/login/?next=/app/dashboard/`,
    `demo@example.com` / `demo123` authenticates, dashboard 200.

## Additional defects found while verifying the driver surface

16. **Authenticated user with no active membership got a 500 on every app page.**
    Memberships are deactivated rather than deleted (and `seed_demo` retires old demo accounts the
    same way), so an account can authenticate while belonging to nothing. `request.organization` was
    then `None` and views dereferenced it immediately — `dashboard` raised
    ``AttributeError: 'NoneType' object has no attribute 'timezone'``. ``_render`` did guard with
    `Http404`, but only *after* each view had already read the attribute, so the guard never ran.
    *Proof:* the retired `dispatcher@example.com` (membership `active=False`, user still
    `is_active=True`) logged in and 500'd on `/app/dashboard/`.
    **Fix:** added the ``active_organization_required`` decorator (21 views) which checks the
    membership at the view entry point and redirects to a new `/no-organization/` page that explains
    the situation and ends the session. `private_media` is deliberately left unwrapped and instead
    returns 404 when the membership is missing, because a file endpoint must fail closed rather than
    redirect. New template `templates_jinja2/registration/no_organization.html`; the email is passed
    explicitly because `logout()` replaces `request.user` before the render.
    Regression test: `tests/integration/test_organization_lifecycle.py`.

17. **Driver stop page crashed with a 500 for depot and break stops.** 12 of 36 seeded stops have
    ``order = NULL`` — `DEPOT_START`, `DEPOT_END` and `BREAK` are real stop rows with no delivery.
    `driver/stop.html` read `stop.order.delivery_address.one_line` unguarded, so opening a depot stop
    raised ``jinja2.exceptions.UndefinedError: 'None' has no attribute 'delivery_address'``.
    **Fix:** the template now derives heading, address and actions from the stop type, falling back to
    ``stop.address`` or the coordinates and hiding the POD/load/instructions blocks for non-delivery
    stops. The view also gained ``order__delivery_address`` in ``select_related`` (it was an N+1).
    Verified: depot stop 347 → 200 "Depot start / no street address recorded"; delivery stop 348 →
    200 with the real address; all 14 driver1 stops and all 6 route detail pages return 200.
    Regression test: `tests/integration/test_driver_stop_types.py`.

18. **Proof of delivery could be recorded against a non-delivery stop.** `driver_pod` accepted any
    stop owned by the driver, so a signature could be filed against a depot or break stop.
    **Fix:** the view rejects stops with no order (redirect plus an explanatory message), and the
    template label is guarded defensively as well. Verified: POD on a depot stop → 302 back to the
    stop, POD on a delivery stop → 200.

19. **`driver/today.html` dereferenced ``next_stop.order.customer.name`` unguarded.** `customer` is
    optional on an order, so a walk-in collection would have failed the render. Fixed to fall back to
    the order reference and then the stop address.
